# SFPI compiler campaign audit — 2026-09-30

This is a read-only audit of the current local/remote state, except for this file. It is **not** a compiler patch, a re-run of the device campaign, or a claim that the concurrent PR-prefix tests have finished. The workflow tree is `../craq-sfpi` (`main` at `ce4fbb3f95cb`); this SFPI source tree is `nkapre/sfpi` at `281d82b0968d`; its GCC submodule is `566071bf728e`. Numbers below are tied to those snapshots and to the named evidence packages, not to whatever a moving branch later contains.

## Verdict

The campaign has real compiler mechanisms, substantial tests, a plausible semantic-C++/knob search process, and credible measured **profile** results. It is **not yet an upstream-ready 31-PR series or a reproducible, unified LLK admission**. The central gaps are (1) no verified DejaGNU result for *each* PR prefix yet, (2) oversized and entangled review slices, (3) no single current source/compiler/profile tuple carrying runtime, formal, exhaustive and ULP gates, (4) one unresolved licensed-knob correctness failure, and (5) machine evidence and documents that lag their own later corrections. A green GitHub status currently means security scanning, not build/test CI.

The concurrent agent is relocating tests to the first PR that supplies each dependency and running `rvtt.exp` on 55 prefixes. Those 55 `.sum` files are the right missing evidence: compare each prefix's unexpected failures against a same-environment baseline and the full stack, and attach the exact commit, flags and `.sum`/`.log`. **Pending** until the artifacts exist and are inspected; this audit does not count them as PASS.

PR #25 changes that shared combiner and #48 changes an existing scheduler, so “new passes default off” does not establish flags-off behavioral identity for those slices. See [riscv.opt](gcc/gcc/config/riscv/riscv.opt), [the combiner](gcc/gcc/config/riscv/tt/gimple-rvtt-combine.cc), and [dst ownership](gcc/gcc/config/riscv/tt/rtl-rvtt-dst-ownership.cc).

The maintainer's requested review form is stable whole-function assembly ([UPSTREAMING_PLAN.md](gcc/docs/UPSTREAMING_PLAN.md)). At each prefix, require at least one observable output/body regression plus a refusal/negative control for each transform, not just a pass-internal dump. The standalone #22 has this shape; the giant substrate and several later slices do not yet demonstrate it locally. The full superproject Development workflow and maintainer contact remain outstanding; the plan says the maintainer does not watch PRs automatically.
- Current GCC has 107 Tensix options and six `Init(1)` defaults; `tt-metal` JIT does not supply `-mtt-tensix-*` options by default. The campaign's ON profile activates 38 positive options; it is **not** production-default performance. Its committed 39/36 counts appear to count the ON string's negative token; the positive-option count is 38/35. Fix and validate this before using the report for promotion decisions.

## LLK, tuning and numeric evidence

- The [full sweep](../craq-sfpi/board/evidence/full-sweep-20260929/README.md) is real and internally arithmetical: 284 selected = **259 PASS + 21 declared SKIP + 4 device-open failures** in the primary run; a separate four-row rerun passed. The combined **263 bounded-correctness PASS** is a justified *two-run* statement, not the primary `summary.json` status and not a formal/ULP certificate. At a ±0.5% band, ON versus OFF is **192 faster / 69 flat / 2 slower**. Against handwritten LLKs over 164 comparable rows it is **71 faster / 25 flat / 68 slower** (using the evidence's sign convention); this is a statistical tie, not “263 wins.” The four failures were infrastructure, but preserve the original FAIL and rerun identity in machine-readable aggregation.
- The OFF/ON experiment compares two **profiles**, not “all passes absent versus present.” Sixteen of 38 positive ON options have no explicit OFF spelling and depend on present `Init(0)` defaults; six `Init(1)` passes run in both arms. The branch defines many more toggles than the 38-profile subset. The compile-only firing census shows changed `.text` for options, not correctness or cycle benefit. The knob selector's proposals are hypotheses and explicitly leave formal/exhaustive/ULP/deployment admission `NOT_RUN` ([incremental plan](../craq-sfpi/board/evidence/incremental-knobs-20260929/PLAN.md)). Its paired three-repeat/median/±0.5% method is sound as a *marginal* screen, but joint/drop-one and preconditioned groups must not be interpreted as isolated wins.
- I independently rolled up the incremental result summaries: **40 groups, 938 group-op runs, 937 PASS / 1 FAIL; 162 faster / 713 flat / 62 slower** at the stated band. These are repeated group-op cells, **not unique LLK wins**. The failure is `castfp32tofp16a` with `sem_on/correctness exit 1` under `s05-stochrnd-store-fold` ([group-results.tsv](../craq-sfpi/board/evidence/incremental-knobs-20260929/results/s05-stochrnd-store-fold/group-results.tsv), row 34). This flag is licensed/value-changing and excluded from the ordinary selector, which contains the deployment risk, but its correctness failure is unresolved. Raw per-run trees are node-local and deliberately not committed ([RAW-RUNS.md](../craq-sfpi/board/evidence/incremental-knobs-20260929/results/RAW-RUNS.md)); the exact failing log/ELF cannot be rechecked from the committed table alone.
